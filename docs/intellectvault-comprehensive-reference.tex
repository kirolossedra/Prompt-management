\section{Purpose and Evidence Standard}

This reference describes the implementation present at repository commit
\commit{7e45248a408e372088d18cab74faef5a79523075}. Current source code and Git
commits are authoritative for what exists. GitHub Issues, Issue comments, and
actual labels are authoritative for explicitly raised open scope.

The roadmap intentionally does not infer future delivery dates, priorities,
completion percentages, dependencies, or strategic initiatives. An open Issue
is also not treated as proof that its implementation is absent: several Issues
remain open after corresponding code landed.

\section{Current Product Shape}

EurekaVault is a private, version-controlled Prompt and methodology workspace.
Its current implementation combines:

\begin{itemize}
  \item a React 19 + TypeScript + Vite frontend;
  \item Firebase Authentication and owner-scoped Realtime Database storage;
  \item automatic Prompt-local version history and Git-style comparison;
  \item Global Version snapshots;
  \item Prompt attachments and directed Prompt lineage;
  \item Mindsets, Preferences, Decisions, activity, and Achievements;
  \item conventional Prompt/history search;
  \item authenticated Gemini-backed Finder, Repurposer, Mixer, and Prompt Blocks;
  \item a Spring Boot 4.1 / Java 21 backend foundation hosted through Render/Docker;
  \item GitHub Actions quality and deployment gates.
\end{itemize}

\section{Runtime Architecture}

\begin{verbatim}
React browser application
  |-- Firebase Authentication
  |-- Firebase Realtime Database
  |     current owner-scoped vault CRUD path
  |
  |-- Netlify Functions
  |     current authenticated Gemini boundary
  |     |-- Semantic Finder
  |     |-- Repurposer
  |     |-- Mixer
  |     `-- Prompt Blocks transformation
  |
  `-- Spring Boot / Render
        incremental 3-tier migration foundation
        current public application role: infrastructure health
\end{verbatim}

The physical deployment is multi-service, but the application data path is not
yet fully 3-tier. The browser still performs direct Firebase data access and AI
requests still use Netlify Functions. The Spring Boot service must therefore be
described as a migration foundation, not as the completed application API.

\section{Data and Version-Control Model}

The direct hierarchy is:

\begin{verbatim}
Endeavor -> Task -> Prompt -> Prompt Version
\end{verbatim}

The owner-private data root is
\code{intellectVault/users/\{firebaseUid\}/}. Firebase rules require the
authenticated UID to match the path UID.

Prompt history is automatic: creating a Prompt establishes Version 1 and saving
a changed Prompt creates a new historical snapshot. Restoring historical content
creates another current version rather than deleting later history. Global
Versions are separate, deliberate vault-wide snapshots.

\section{Knowledge and Methodology Features}

\subsection{Prompt files}

Prompt attachments are Base64-backed and bounded by application limits of 2 MiB
per file, 20 files per Prompt, and 10 MiB aggregate per Prompt.

\subsection{Prompt lineage}

Directed \code{inspired-by / inspires} relationships are explicit user-created
lineage edges. Duplicate and cyclic edges are rejected. GitHub Issue \#15 asks
whether an ``instance'' model should replace this concept, but that Issue is a
design proposal, not an approved migration.

\subsection{Mindsets and Preferences}

Mindsets are scoped methodology artifacts. Mindset Construction deterministically
assembles selected Prompt material and does not call Gemini. Preferences are
persisted according to the scopes implemented in the current domain model.

\section{AI Boundary}

Current AI calls go through authenticated Netlify Functions; the Gemini key is
not sent to the browser. The client supplies a Firebase ID token and the server
boundary verifies the authenticated user context before invoking Gemini.

Data is scoped per operation. Finder receives a bounded searchable Prompt corpus;
Repurposer receives one source Prompt plus an objective; Mixer receives selected
Prompt sources; a Prompt Blocks transform receives only the content and ordered
constraints required by that block.

Generated content is non-destructive until an explicit persistence action occurs.

\section{Prompt Blocks}

Prompt Blocks is a deterministic Prompt-processing directed acyclic graph rather
than a generic autonomous-agent framework. The MVP landed in \commit{b556e64},
with correctness fixes in \commit{e079616} and \commit{90b6799} and live-workspace
refinements in \commit{7e45248}.

Implemented behavior includes:

\begin{itemize}
  \item current or pinned Prompt inputs and direct user inputs;
  \item typed content and constraint connections;
  \item multiple Prompt transformation operations;
  \item Mindset and extracted-style constraints with explicit priority;
  \item As Is, Summarized, and Conclusion Only outputs;
  \item deterministic DAG validation, cycle rejection, and topological execution;
  \item inspectable intermediate results and downstream blocking on failures;
  \item temporary and persisted pipelines;
  \item editable Firebase-backed transformation prompts;
  \item explicit output persistence through the existing Prompt/version lifecycle;
  \item desktop visual editing and a dedicated mobile interaction model;
  \item deterministic beautification, printing, compact IDE-style controls, an
        output-intent warning, and reachable scrolling run output.
\end{itemize}

Issue \#7 remains open and contains broader design exploration. This reference
does not interpret every idea in that Issue as promised follow-up work.

\section{EurekaVault Identity}

The naming and visual identity work is supported by GitHub Issue \#9 and commits
including \commit{3b61d70} and \commit{349b24f}. The code contains the
EurekaVault name, epsilon mark, Alexandrian lighthouse motif, Greek identity copy,
and a light-blue/gold/royal-red palette. The Issue remains open, so the rebrand is
described as partially implemented rather than declared complete.

\section{Spring Boot Migration}

GitHub Issue \#12 carries the \code{architecture} and \code{epic} labels. Its
owner comment explicitly states: ``It's gonna be springboot.'' Commit
\commit{4a3cc23} introduced the Spring Boot 4.1 / Java 21 service, health endpoint,
Docker packaging, and Render configuration.

The migration is incremental. Current Firebase CRUD and current Netlify Gemini
paths remain active. A deployed health endpoint does not by itself make the
application functionally 3-tier.

\section{CI/CD}

Commit \commit{3d2bfa9} introduced frontend and backend quality gates plus a
post-CI production deployment workflow. The checks include frontend lint/tests/
build, Netlify Function syntax validation, Maven verification, and a Dockerized
Spring Boot health smoke test. Commit \commit{54373c9} added Netlify build-hook
gating; later commits corrected CI issues.

GitHub Issue \#16 remains open because the production workflow is not currently
path-split: a frontend-only change can still cause the backend deployment job to
run after successful main-branch CI.

\section{Security Notes}

\begin{itemize}
  \item Realtime Database authorization is owner-scoped by Firebase UID.
  \item Gemini credentials stay on server-side execution boundaries.
  \item Prompt Blocks runtime output does not persist automatically.
  \item Prompt Blocks default transform strings exist in the client bundle and
        therefore are not secrets.
\end{itemize}

Commit \commit{54373c9} accidentally tracked deployment-hook URLs in a local
environment file. Commit \commit{daa6f7b} removed that file, but Git history
retains deleted values. Those hooks should be treated as exposed and rotated if
that has not already happened. Their values are intentionally omitted here.

\section{Removed Unsupported Roadmap Commitments}

Older generated documentation presented markup-defined hierarchy parsing,
collaboration, formal Mindset inheritance/conflict semantics, Preference precedence,
and workspace deletion as future product initiatives. The inspected GitHub Issue
set contains no corresponding Issue/epic for those items. They are therefore not
part of the evidence-backed roadmap.

Current facts may still be stated---for example, the workspace is owner-private---
without turning the absence of another feature into a promise to build it.

\section{Roadmap Maintenance Rule}

For future updates:

\begin{enumerate}
  \item use current code and commits to establish delivered behavior;
  \item use GitHub Issues/comments/labels to establish explicitly raised scope;
  \item keep GitHub open/closed state separate from implementation evidence;
  \item use actual GitHub Milestones only if the owner creates them;
  \item do not infer delivery dates, percentages, priorities, dependencies, or epics.
\end{enumerate}

This preserves a roadmap that reports the owner's project rather than silently
turning analysis into commitments.
